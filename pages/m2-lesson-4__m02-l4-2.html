The Core Question

Working code is not the same as a working system.

A model can run without errors and still produce results that are wrong, unfair, or harmful. The cause is almost always upstream: in the data, the labels, the splits, or the gaps. This lesson is how you read a failure backward to its source.

Animation showing failure tracing back to its cause

Failure Defined

A working model that produces results the user, the developer, or the affected community would not stand behind.

Three Sources of Data Failure Click to expand or collapse this section.

Where bad data comes from

Three sources. Three repair strategies.

When a model behaves badly, the data is usually the cause. Three patterns explain almost every real-world failure, and each one has a different fix.

Some groups are underrepresented

Imbalanced

The model learns the majority and ignores the minority. Fix: oversample the minority, or weight it higher during training.

The world has changed since collection

Stale

The model uses outdated patterns to predict current outcomes. Fix: schedule regular retraining.

Training data differs from production data

Mismatched

The model learned one distribution and meets another. Fix: monitor the gap and retrain when it widens.

Key Point: Most production failures fall into one of these three buckets. Naming which one is half of the fix.

Code Works, Model Fails Two stories of the same morning.

Two engineers, same morning, both with code that runs cleanly. One model ships, one model ships harm. The difference is upstream of the code.

Code-only review

Engineer A

Confirmed: code runs, accuracy is 92 percent

Ships the model.

The engineer checks the script, runs the test, sees 92 percent. They merge and deploy. Three weeks later the model is quietly rejecting valid applications from a specific neighborhood. The code is fine; the training data was not.

Code-plus-data review

Engineer B

Same accuracy, also disaggregated by group

Catches the gap before deploy.

Same code, same accuracy. But the engineer pulled the per-group accuracy table. They notice the 92 percent average hides a 70 percent score on one group. They block the deploy and request more representative data. Same code; different outcome.

The Bias Map

Five entry points. One audit per point.

Bias is not a property of the model. It is a property of the data and the choices that produced it. The good news: it can only enter at five specific places, and each one is auditable.

From Collection to Production

Every model has a pipeline. Bias hides in the gaps between steps. The fix is to put a check at each one.

1. Collection

Who or what generated the raw data. Sampling decisions, instrument choices, who got measured.

2. Labels

Who applied the labels, under what guidelines, with what speed pressure.

3. Sampling

How rows were selected for training. Random? By time? By region? Each choice has a downside.

4. Design

Which features were chosen, which were dropped, what counted as the target. Every choice is a judgment.

Collection: What got measured.

Labels: Who decided the answer.

Sampling: Which rows made it in.

Deployment: What changes once the model meets reality.

The Four Failure-Hunt Questions Open this to see the questions every analyst asks when a model goes wrong.

Failure Triage

Four questions. One per failure mode.

When a model produces a wrong or unfair result, do not start with the code. Start with the data, in this exact order. The answers usually surface the cause within an hour.

Q1

Is the training data representative?

Pull a per-group accuracy table. Any group below the average is a candidate for the failure source.

Q2

Are the labels honest?

Sample 50 labels by hand. Check who labeled them, when, and under what guidelines.

Q3

Is the data still current?

Check the timestamp. If the data is older than the world has changed, the model is using outdated patterns.

Q4

Does production data look like training data?

Compare basic statistics: mean, standard deviation, distribution. Drift here is a silent killer.

Result: Four answers, four short notes. They take an hour. They almost always surface the cause before anyone needs to open the model code at all.

Common Failure-Analysis Mistakes Open this section to review the traps.

'Blame the model architecture first'

Architecture is almost never the cause of an unfair or wrong model. Data is the cause. Spending two weeks tuning the model when the data is broken is a common, expensive mistake.

'If the accuracy is high, there is no problem'

Aggregate accuracy hides per-group harm. A 92 percent model can be 70 percent for one group. The number you average is the number you ignore.

'Bias only matters in social applications'

Bias shows up in weather models, recommender systems, and medical screens. Anywhere the world is uneven, the model will be too, unless someone audited the data.

Key Takeaways

What you should remember from Lesson 4

Garbage in, garbage out. No algorithm fixes bad data. The cleanup is the work, not a step you can skip.

Bias enters at five places. Collection, labels, sampling, design, and deployment. Knowing where it entered tells you how to fix it.

Suspicious labels are louder than missing data. Spend the first hour of any new dataset auditing the labels. The cost of doing it later is always higher.
